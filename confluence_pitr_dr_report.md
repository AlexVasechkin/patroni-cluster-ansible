# DR-тестирование PITR: Patroni + pgBackRest

> **Статус:** ✅ ПРОЙДЕНО (8/8 сценариев) · **Дата:** 2026-08-07 · **Кластер:** `pg-cluster` · **Владелец:** DBA

Проверка резервного копирования и аварийного восстановления PostgreSQL-кластера
под управлением Patroni с бэкапами в pgBackRest. Ниже — краткие итоги; подробные
прогоны с командами — в отчётах `test1…test8` и `pitr_restore_report.md`.

---

## 1. Область и стенд

| Параметр | Значение |
|---|---|
| Топология | Patroni: `pg1`/`pg2`/`pg3` (1 Leader + 2 streaming), DCS — etcd (mutual TLS) |
| Бэкапы | pgBackRest, репо-хост `backup1`, шифрование `aes-256-cbc`, сжатие `zst` |
| Архивация WAL | непрерывная, `archive_timeout=60s` |
| Расписание | full — еженедельно, diff — ежедневно, **incr — ежечасно**, verify — еженедельно |
| Нагрузка | pgbench (OLTP, scale 10) |

## 3. RTO и RPO (главное)

- **RPO (сколько данных теряем):** при одновременной потере storage на всех нодах
  теряется только **незаархивированный хвост WAL** — ограничен `archive_timeout`
  (**≤ 60 c** записи). Чистая остановка/graceful shutdown потерь не даёт.
- **RTO (сколько восстанавливаемся):** = почти-константный raw-restore (зависит от
  размера БД) **+ накат WAL**, который растёт линейно с объёмом (**≈41 МБ/с**).
  Главный рычаг снижения RTO — **частые incr-бэкапы** (короткая цепочка WAL).

---

## 4. Что подтвердилось

- **Disaster recovery работает end-to-end:** restore → промоут нового Leader →
  автоматическое пересоздание/догон реплик (в т.ч. через `pg_rewind`).
- **Оба режима PITR:** disaster-DR «до последнего WAL» (`--type=default`) и точечный
  откат по времени (`--type=time`) — один и тот же bootstrap-механизм Patroni.
- **Fail-safe при сбоях инфраструктуры:** недоступный/переполненный/повреждённый
  репозиторий → явные ошибки и ненулевые коды, без «тихой» потери или полу-бэкапов.
- **Целостность:** после каждого восстановления инвариант данных pgbench сходится,
  реплики бит-в-бит совпадают с Leader.

## 5. Рекомендации (для прода)

1. **Мониторинг и алерты** (критично): `pg_stat_archiver.failed_count`↑ и свежесть
   `last_archived_time`; свободное место на репо-хосте и под `pg_wal`; ненулевой
   rc бэкап-обёртки `pgbackrest-backup.sh`; результат еженедельного `verify`.
2. **Снижение RPO:** уменьшить `archive_timeout` и/или синхронная репликация /
   offsite-standby в другой ЦОД.
3. **Снижение RTO:** сохранить частые incr-бэкапы; быстрый/локальный доступ к репо.
4. **Избыточность репозитория:** offsite (`repo1-type=s3/gcs`) + второй репозиторий
   `repo2` — устранить SPOF `backup1`.
5. **Автоматизировать restore-drill:** периодический out-of-place restore последнего
   бэкапа + старт временного PG + проверка консистентности и замер RTO (безопасно,
   без остановки прода). — *единственный незакрытый пункт DR-раздела.*

---

## 6. Процедурные заметки (грабли)

- Реальный каталог данных — `/var/lib/postgresql/16/data` (не `.../main`).
- Для **честного** DR-теста нельзя «ронять» Patroni через `SIGKILL` при живом DCS —
  systemd/Patroni самозалечат кластер и замаскируют RPO. Порядок: убить PG →
  чистый `systemctl stop patroni` → очистить DCS → restore.
- `pgbackrest expire --set=<label>` — штатное точечное удаление бэкапа.
- Регулярный restore-drill измерять out-of-place (отдельный PG на порту), не трогая
  боевой кластер.
